## AC 1 — `read_parquet([24 segmen])` vs file tunggal

p50 / p95 dalam ms. Rasio = p95 segmen ÷ p95 file tunggal. Hasil **identik di 14/14 query pada kedua run**.

| group-by teks: c7 → count, sum(c3), urut count | 270 / 301 | 268 / 331 | 1,10 | 276 / 355 | 277 / 352 | 0,99 | ya |
| totals widget (`buildTotalsSql`) | 37 / 44 | 41 / 48 | 1,09 | 42 / 56 | 43 / 63 | 1,12 | run 2 tidak (+7 ms) |

**Putusan AC 1 (dibaca harfiah): tidak lolos.** Hasil identik lolos; p95 ≤ 1,1× lolos di 8/14 query pada kedua run,
gagal konsisten di 3 query (halaman terakhir tanpa urut, count tanpa filter, filter-values tanggal) dan gagal di
salah satu run pada 3 query lain (selisih +4–7 ms, run lainnya lolos → derau mesin terbebani).

Penjelasan yang terukur:

1. **Query berat (≥ 100 ms: group-by, urut, filter-values teks): rasio 0,92–1,10.** Biaya pemindaian sama; 24
   file tidak menambah ukuran data (223,1 vs 223,5 MB).
2. **Overhead tetap per file ± 0,11–0,14 ms.** Probe skala (`scale.ts`, 20 putaran, data sama dipecah 1 / 24 / 60
   file, hasil identik): count tanpa filter p50 1,6 → 4,8 → 8,3 ms; tabel halaman 1 10,0 → 11,1 → 19,0 ms;
   filter-values tanggal 24,0 → 24,2 → 29,5 ms; group-by teks 154 → 155 → 161 ms. Pada query kecil overhead ini
   membuat rasio tinggi, tetapi selisih absolutnya ≤ 13 ms di p95 (≤ 9 ms di 60 file untuk p50).
3. **Halaman dalam tanpa urut = sort penuh `_row`.** `EXPLAIN ANALYZE` (`probe-deep.mjs`): CTE `ids`
   (`ORDER BY _row LIMIT 100 OFFSET 9.599.900`) mengurutkan 9.600.000 baris di kedua varian; materialisasi
   `_row IN ids` sesudahnya hanya 7–8 ms karena filter dinamis `_row >= …` turun ke scan. Sort penuh atas daftar
   24 file 204 → 248 ms p50. Ini bukan I/O dan hanya terjadi tanpa urut + OFFSET dalam; jalur jendela AC 2
   menyelesaikan kasus yang sama dalam 12–16 ms (lebih cepat dari 150 ms file tunggal hari ini).

## AC 2 — Posisi global → (segmen, `file_row_number`), jendela 200 baris

Jumlah baris per segmen dibaca dari metadata (`count(*)` per file, pengganti kolom DB); hanya segmen yang beririsan
dibaca: `read_parquet($sK, file_row_number = true) WHERE file_row_number BETWEEN $aK AND $bK`, `UNION ALL`, urut
`(k, file_row_number)`. Pembanding kebenaran: `file_row_number BETWEEN p AND p+199` pada file tunggal (seluruh
11 kolom dibandingkan per sel). 100 posisi acak (seed 34) + 5 posisi yang melintasi batas segmen.

| | Run 1 segmen | Run 1 tunggal | Run 2 segmen | Run 2 tunggal | Baris salah |
|---|---|---|---|---|---|
| 100 posisi acak: p50 / p95 / maks (ms) | 12,2 / **14,6** / 17,1 | 13,5 / 17,5 / 21,5 | 12,5 / **16,3** / 22,7 | 14,0 / 17,0 / 21,6 | 0 / 100 (kedua run) |
| 5 jendela lintas batas: p50 / p95 | 11,6 / 11,9 | 13,1 / 16,1 | 13,2 / 14,5 | 14,7 / 16,1 | 0 / 5 |

**Lolos** (p95 ≤ 50 ms, semua baris benar). Parameter `$aK/$bK` (angka JS → BIGINT) tetap di-pushdown: rencana
menampilkan `Filters: file_row_number>=…` di scan, waktu parameter vs literal sama (21–28 vs 22–23 ms, `SELECT *`
13 kolom pada file tunggal).

## AC 3 — Daftar path sebagai parameter dengan sandbox, campuran segmen legacy + baru

Campuran 21 file: `legacy.parquet` (baris segmen 1–4) + 16 segmen baru (`seg-05..20`, `_row BIGINT`, tanpa c11) +
4 segmen baru dengan kolom tambahan c11 (`seg-21..24-c11`). Pembanding: file tunggal dengan
`c11 = CASE WHEN _row >= 8.000.002 THEN c4 * 2 END`. Query: 14 query AC 1 + 8 query khusus (count/sum/group-by
c11, `c11 IS NULL`, halaman di akhir legacy / awal segmen baru / awal segmen c11, urut c11 desc, `typeof(_row)`).

| Cara membaca | Hasil (kedua run) | Putusan |
|---|---|---|
| Daftar polos, legacy di depan | query tanpa c11 identik; query c11 → `Binder Error: Referenced column "c11" not found`; mini (`_row` BIGINT 3.000.000.000 setelah file INTEGER) → `Conversion Error … can't be cast … INT32`; halaman tabel → galat BLOOM_FILTER (probe) | gagal, bergantung urutan |
| Daftar polos, segmen c11 di depan | `schema mismatch in glob: column "c11" … could not be found in file seg-05` | gagal |
| `read_parquet($path, union_by_name = true)` | 19/22 identik; **3/22 galat** (halaman tabel: `table_first`, `table_sort_text`, `c11_sort_desc`): `Not implemented Error: Can't convert TableFilterType (BLOOM_FILTER) from global to local indexes` | gagal |
| **Proyeksi eksplisit** per kelompok skema: `SELECT CAST(_row AS BIGINT) AS _row, c1..c10, CAST(NULL AS BIGINT) AS c11 FROM read_parquet($g0) UNION ALL … read_parquet($g1) UNION ALL SELECT _row, c1..c11 FROM read_parquet($g2)`, tiap `$gN` = `listValue` | **22/22 identik**, `typeof(_row)` = BIGINT; 5 jendela AC 2 yang melintasi batas legacy→baru dan tanpa-c11→c11 benar (p95 23–24 ms) | **lolos** |

Lingkup bug `union_by_name` (`probe-ubn.mjs`, query halaman tabel `_row IN (SELECT _row FROM ids)`): gagal bila tipe
`_row` berbeda antarfile (legacy + `seg-05` saja sudah cukup), **juga dengan daftar polos**; berhasil bila hanya set
kolom yang berbeda (`seg-20` + `seg-21-c11`) atau skemanya identik. Pemicunya filter bloom dari hash join yang
diturunkan ke scan kolom yang perlu cast.

Sandbox dan binding (`@duckdb/node-api` 1.5.6-r.1):
- `listValue([...])` tanpa tipe eksplisit berfungsi sebagai parameter `read_parquet($path)` di bawah sandbox.
- Larik JS biasa ditolak (`Cannot create values of type ANY`); larik JS + tipe `LIST(VARCHAR)` ditolak
  (`input is not a DuckDBListValue`); `listValue([])` ditolak (`Cannot create lists with item type of ANY`) →
  manifest kosong harus ditolak sebelum query.
- Daftar yang memuat satu path di luar `allowed_directories` (`/etc/hosts`) → seluruh query ditolak
  `Permission Error … file system operations are disabled by configuration`; `…/data/../luar.parquet` juga ditolak.
  Glob di dalam direktori yang diizinkan diterima, jadi path harus selalu berasal dari manifest, bukan dari user.
- `QueryEngine.exec` dan `BuiltSql.params` hari ini bertipe skalar; skrip memakai cast — T-037 harus melebarkan
  tipenya ke `DuckDBValue`.

Biaya proyeksi eksplisit vs pembanding (informatif, run 2; pembanding sendiri memakai subquery `CASE` sehingga
sedikit lebih lambat dari file tunggal polos): query berat 0,92–1,11×; halaman dalam 1,04–1,46×; **count tanpa
filter 2 → 41 ms** (UNION ALL mematikan count dari metadata); **count dengan filter 93 → 140 ms p50** (`union_by_name`
65 ms — penyebab belum diselidiki); `typeof(_row)` 12 → 49 ms. Proyeksi hanya diperlukan bila skema segmen berbeda.

## Lolos/tidak terhadap AC

- **AC 1:** hasil identik **lolos**; p95 ≤ 1,1× **tidak lolos** secara harfiah (3 query konsisten, 3 query di satu
  run). Query ≥ 100 ms lolos kecuali halaman dalam tanpa urut (1,45–1,49×, ada mitigasi jalur jendela).
- **AC 2:** **lolos** (p95 14,6 / 16,3 ms, 0 baris salah).
- **AC 3:** **lolos dengan proyeksi eksplisit**; `union_by_name` dan daftar polos **tidak** (galat DuckDB 1.5.6,
  bergantung urutan).
- **AC 4:** di luar skrip: draf ADR (opsi A–F, tabel biaya ops per unggahan, keputusan, kriteria fallback) dan teks
  amandemen flow-kerja A4/D4/D15/D16 disiapkan untuk ditinjau pemilik; ADR accepted, flow-kerja, dan penutupan
  T-015 menunggu pemilik.

## Caveat

1. **SSD lokal + cache OS hangat**, satu query pada satu waktu. Olympus memakai HDD bersama (T-024: load 20–57,
   tekanan I/O 20–85 %); membaca 24 file dingin di HDD berarti lebih banyak seek daripada satu file. Belum diukur.
   Sebaliknya, segmen mengurangi unduhan ulang cache app per unggahan ± 10× (T-024: 600 MB ≈ 109 s di olympus).
2. **Mesin terbebani** (load 6–9 di 10 core): p95 dari 30–40 sampel bergeser ± 10–15 % antar-run (contoh:
   group-by teks 1,10 lalu 0,99). Rasio di bawah ± 1,15 pada query < 60 ms tidak bisa dibedakan dari derau.
3. Data 10 kolom (bentuk csv T-024), bukan xlsx 30 kolom; footer parquet tumbuh dengan kolom × row group, jadi
   overhead per file pada sheet lebar kemungkinan lebih besar. Data dibangkitkan DuckDB, bukan lewat `writeTyped`
   (tata letak sama: zstd, row group 122.880, 1 thread).
4. Segmen berukuran sama (400 rb); bulan nyata bervariasi. Konkurensi 4 slot, `ParquetCache` (sewa batch,
   unduhan), dan cache hasil tidak diukur.

## Belum diverifikasi

- VM T-023 / olympus (4 vCPU, HDD), cache dingin, 13 jt baris, 60–120 segmen pada sheet 30 kolom (P-29/T-061,
  P-31/T-063).
- Sewa batch 24–60 kunci di `ParquetCache` dan unduhan bersamaan (T-037 AC 2).
- Penyebab count berfilter lebih lambat lewat proyeksi eksplisit (UNION ALL) dan apakah normalisasi segmen lama
  (tulis ulang dengan kolom NULL / `_row BIGINT`) lebih murah daripada proyeksi permanen.
- Recast per segmen, GC mark-and-sweep, ekspor T-017 dengan N segmen, sampel skema.
- Perilaku DuckDB/node-api versi lain (bug `union_by_name` bisa sudah atau belum diperbaiki).
