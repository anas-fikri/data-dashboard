# T-006 — Perf ingest tahap raw (file → raw.parquet per sheet)

- **Tanggal:** 2026-10-12
- **Mesin:** Apple M4 (10 core), RAM 16 GB, SSD lokal; macOS; Node 26.0.0; DuckDB 1.5.6 (`memory_limit` 1 GB, `threads` 2 sesuai D7).
- **Beban mesin saat uji:** load average 6–9. Container proyek lain (`global_postgres`) memakai ± 100% CPU, jadi angka waktu bersifat konservatif.
- **Perintah:** `npx tsx --conditions=react-server scripts/perf-ingest.ts <fixture>`.
  - Skrip menjalankan `runIngest` sungguhan: parser ADR-0005, DuckDB appender, lalu COPY ke Parquet deterministik.
  - Database dipalsukan in-memory. Storage lokal memakai hard link dan rename, sehingga waktu transfer jaringan ke RustFS tidak ikut terukur.
  - Upload/unduh 1 GB lewat jaringan diukur di T-024.
- **Fixture:** `tests/fixtures/README.md` (perintah `make-fixture` untuk xlsx teks-berat 1 GB dan csv 1 GB).

## Hasil

| Fixture | Waktu | CPU | Puncak RSS (kernel) | Hasil |
|---|---|---|---|---|
| xlsx teks-berat 946 MB (3 sheet × 1.000.003 baris × 30 kolom, 40 juta shared strings) | **256 s** (4,3 menit) | 284 s | **1.018 MB** | 3 sheet, `rawRows` 1.000.002 per sheet, headerRow 3 (benar), raw.parquet total 597 MB |
| csv 974 MB (8.100.001 baris × 10 kolom, titik koma, desimal ID) | **41 s** | 39 s | **1.071 MB** | 1 sheet, `rawRows` 8.100.001, raw.parquet 207 MB; disk temp puncak ± 2,1 GB |

Run pertama xlsx: 334 s, 897 MB. headerRow saat itu tertebak 4 karena header fixture punya banyak nama duplikat. Heuristik diperbaiki: proporsi sel teks menjadi penentu utama dan keunikan hanya penentu sekunder. Run kedua menebak baris 3 dengan benar (324 s, 884 MB).

Angka di tabel adalah run ketiga, setelah perbaikan review putaran 1. Perubahan pada run ini:
- parser membungkus error per file;
- pemeriksaan internal saxes dilakukan per chunk;
- tabel raw tumbuh ×2 lewat buat-ulang tabel;
- flush batch berdasarkan baris atau jumlah karakter.

Puncak RSS naik ± 130 MB tetapi tetap jauh di bawah 2 GB.

## Lolos/tidak terhadap AC

- **AC 6 (xlsx 1 GB < 15 menit, puncak RSS < 2 GB):** lolos (4,3 menit; 1.018 MB).
- **Disk temp:** sisa disk minimum selama proses turun ± 2,3 GB pada run terakhir; run awal mencatat ± 4,5 GB. Sisa disk mesin ini juga dipengaruhi proses lain. Isinya file sumber (hard link), tabel DuckDB per sheet, spill sharedStrings, dan Parquet. Ini sesuai kebutuhan "ukuran upload + ≤ 8 GiB" di ADR-0005 dan catatan T-023.

## Catatan

- **Pembagian waktu xlsx:** ± 200 s parse (T-005), sisanya append DuckDB (± 23 s per juta baris × 30 kolom) dan COPY Parquet.
- **Optimasi lanjutan bila T-024 di VM minimum mendekati batas:** `appendDataChunk` (vektor) menggantikan append per nilai, dan pipeline parse/append paralel per sheet.
- **CSV melewati JS hanya untuk pindai byte** (jumlah kolom, baris kosong, validitas UTF-8 seluruh file) dan transcode Windows-1252. Pembacaan dan Parquet sepenuhnya di DuckDB: `read_csv` dengan kolom eksplisit, satu pembaca (`parallel = false`), dan `buffer_size` 32 MB agar muat di `memory_limit`.
- **CSV setelah review putaran 1: 41 s, sebelumnya 50 s.**
  - Nomor baris fisik kini diambil dari `rowid` tabel muat, bukan window `row_number()`.
  - Bila ada baris kosong, ditambah offset lewat ASOF JOIN sempit dan POSITIONAL JOIN.
  - Window menyimpan semua kolom per blok, sehingga CSV 1.100 kolom OOM di 256 MB walau hanya 2 baris.
  - Uji sintetis 3 juta baris × 20 kolom dengan 640 ribu baris kosong: agregat 0,7 s (sebelumnya 5,7 s), COPY 6,8 s (sebelumnya 14,7 s).
- **Tabel lebar (batas 2.048 kolom):** hitung sel terpotong memakai satu `list_filter` per baris; N agregat `FILTER` butuh ± 5 s per baris di 2.048 kolom. Sampel header memakai top-N atas `_row` saja, lalu baris-barisnya diambil; top-N atas semua kolom juga OOM pada tabel lebar.
