# T-005 — Benchmark parser xlsx/csv 1 GB

- **Tanggal:** 2026-10-12
- **Mesin:** Apple M4 (10 core), RAM 16 GB, SSD lokal; macOS. Node 26.0.0.
- **Paket:** exceljs 4.4.0, @duckdb/node-api 1.5.6-r.1 (DuckDB v1.5.6, ekstensi `excel`), saxes 6.0.0, yauzl 3.4.0.
- **Pengukuran:** satu parser per proses (`scripts/bench-parsers.ts`). Waktu = parse penuh semua sheet sampai callback baris terakhir. Puncak RSS = sampel `process.memoryUsage().rss` tiap 100 ms, mencakup memori native DuckDB; pada run final juga `process.resourceUsage().maxRSS` dari kernel (angkanya sama). Memori sistem selama uji ± 50% bebas, sehingga kompresi memori macOS tidak menyamarkan angka. Batas pengaman 6 GB RSS per proses.
- **Kebenaran:** jumlah baris terisi, jumlah sel terisi, dan checksum isi teks per sel (XOR fnv1a `baris:kolom:teks`) dibandingkan dengan manifest generator. Pada fixture 2k–100k baris, setiap sel juga dibandingkan langsung dengan model (`--verify`). DuckDB `read_xlsx` mengembalikan semua sel sebagai VARCHAR sehingga checksum teksnya tidak sebanding; kebenarannya dibuktikan `--verify` pada fixture kecil.

## Catatan teknis yang mengikat T-006

1. **DuckDB `read_xlsx` kehilangan kolom secara diam-diam.** Tanpa `range`, lebar tabel diambil dari baris pertama. Baris judul hanya mengisi kolom A, sehingga 21.576 dari 23.579 sel di `kecil.xlsx` hilang tanpa error. Dengan `range` eksplisit, DuckDB memancarkan baris kosong sampai baris 1.048.576 bila batas baris tidak diberikan. Sel tanggal asli keluar sebagai angka serial ("46171").
2. **ExcelJS tidak cocok untuk file Excel nyata berukuran besar.** Pada urutan entri Excel, pembaca streaming macet. Pada urutan sebaliknya, seluruh shared strings dimuat ke heap. Paket juga membawa `uuid` 8.3.2 (GHSA-w5hq-g745-h8pq, CVSS 7.5); di project ini dipaksa ke 11.1.1 lewat npm `overrides` karena ExcelJS hanya devDependency benchmark.
3. **Shared strings adalah sumber memori utama**, sesuai risiko di flow-kerja C. Spill ke file sementara dengan indeks ± 4 byte per string (basis per 1.024 string + offset relatif `Uint32`) menjaga RSS di 323 MB untuk 40 juta string; tanpa spill heap habis di 4 GB. Pada sampel 100k baris, spill tidak memperlambat (12,5 s vs 13 s).
4. **Nomor baris fisik.** sax-yauzl memakai atribut `r`; baris tanpa nilai (termasuk baris yang hanya bergaya) tidak dipancarkan dan nomor baris tetap fisik (dibutuhkan `_row` di raw.parquet). DuckDB hanya memberi urutan baris keluaran.
5. **CSV sebaiknya langsung di DuckDB** (`read_csv` → Parquet tanpa melewati JS). Sniff encoding/delimiter/jumlah kolom dilakukan worker dari 64 KB pertama, lalu kolom diberikan eksplisit agar baris pembuka yang lebih sempit tidak mengacaukan deteksi.

## Lolos/tidak terhadap target

- **AC 2 (RSS > 2 GB → mitigasi):**
  - DuckDB melewati 2 GB (2.266 MB) dan gagal di batas D7 1 GB. ExcelJS gagal.
  - Parser terpilih sax-yauzl + spill: 323 MB, di bawah 1 GB.
  - Lihat ADR-0005.
- **Waktu:** 192 s untuk parse xlsx 1 GB masuk rentang perkiraan flow-kerja C (5–15 menit ingest). T-024 mengukur alur penuh terhadap target < 20 menit. Ruang optimasi bila perlu: pemindai `<c>`/`<v>` khusus menggantikan SAX umum, dan cache LRU shared strings yang lebih besar.

## Review independen

Review T-005 (16 temuan) diperbaiki sebelum angka final: file spill per parse, tag ber-prefix namespace, epoch 1904, deteksi format tanggal kustom, escape `_xHHHH_`, validasi indeks/baris/kolom, batas panjang sel, cek entri zip tumpang tindih dan batas ekspansi relatif ukuran file, CDATA, sel `t="d"`, indeks offset ringkas, checksum teks di benchmark. Kasus tepi diuji di `tests/scripts/parser-sax-edge.test.ts`.

Verifikasi ulang reviewer menemukan batas panjang sel belum membatasi memori (saxes menampung node teks utuh): kini buffer internal diperiksa per potongan stream dan node raksasa ditolak (`parser-sax-edge.test.ts`).

Catatan pengukuran waktu: selisih 192 s vs 280–305 s berasal dari beban mesin (container `global_postgres` proyek lain memakai 100% CPU, load average ± 5). Perbandingan CPU berselang-seling pada `sedang.xlsx` menunjukkan parser final setara versi sebelum pengerasan (median 484 vs 480 ms). Runner kini mencatat `cpuSeconds` selain waktu dinding.

Audit memori menyeluruh (review putaran 5) menutup sisa jalur yang tumbuh mengikuti input: string hasil substring V8 kini disalin mandiri (tidak menahan potongan stream 16 KB), jumlah sharedStrings ≤ 64 juta, file spill ≤ 8 GiB (faktor relatif ukuran file dibuang karena menolak ekspor ERP bertemplate yang sah), metadata entri zip dibatasi, numFmt ≤ 1.000 dan cellXfs ≤ 65.536. Buffer tulis spill 1 MB memangkas ± 95 s CPU syscall pada file 1 GB (293 → 198 s CPU).
