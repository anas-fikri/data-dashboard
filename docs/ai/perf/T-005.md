# T-005 — Benchmark parser xlsx/csv 1 GB

- **Tanggal:** 2026-10-12
- **Mesin:** Apple M4 (10 core), RAM 16 GB, SSD lokal; macOS. Node 26.0.0.
- **Paket:** exceljs 4.4.0, @duckdb/node-api 1.5.6-r.1 (DuckDB v1.5.6, ekstensi `excel`), saxes 6.0.0, yauzl 3.4.0.
- **Pengukuran:** satu parser per proses (`scripts/bench-parsers.ts`). Waktu = parse penuh semua sheet sampai callback baris terakhir. Puncak RSS = sampel `process.memoryUsage().rss` tiap 100 ms, mencakup memori native DuckDB. Memori sistem selama uji ± 50% bebas, sehingga kompresi memori macOS tidak menyamarkan angka. Batas pengaman 6 GB RSS per proses.
- **Kebenaran:** jumlah baris terisi dan jumlah sel terisi dibandingkan dengan manifest generator. Pada fixture 2k–100k baris, setiap sel dibandingkan dengan model (`--verify`).

## Catatan teknis yang mengikat T-006

1. **DuckDB `read_xlsx` kehilangan kolom secara diam-diam.** Tanpa `range`, lebar tabel diambil dari baris pertama. Baris judul hanya mengisi kolom A, sehingga 21.576 dari 23.579 sel di `kecil.xlsx` hilang tanpa error. Dengan `range` eksplisit, DuckDB memancarkan baris kosong sampai baris 1.048.576 bila batas baris tidak diberikan. Sel tanggal asli keluar sebagai angka serial ("46171").
2. **ExcelJS tidak cocok untuk file Excel nyata berukuran besar.** Pada urutan entri Excel, pembaca streaming macet. Pada urutan sebaliknya, seluruh shared strings dimuat ke heap. Paket juga membawa `uuid` < 11.1.1 (advisory moderate).
3. **Shared strings adalah sumber memori utama**, sesuai risiko di flow-kerja C. Spill ke file sementara dengan indeks offset (`Float64Array`) menjaga RSS di bawah 1 GB untuk 40 juta string. Pada sampel 100k baris, spill tidak memperlambat (12,5 s vs 13 s).
4. **Nomor baris fisik.** sax-yauzl memakai atribut `r`, sehingga baris kosong tidak dipancarkan dan nomor baris tetap fisik (dibutuhkan `_row` di raw.parquet). DuckDB hanya memberi urutan baris keluaran.
5. **CSV sebaiknya langsung di DuckDB** (`read_csv` → Parquet tanpa melewati JS). Sniff encoding/delimiter/jumlah kolom dilakukan worker dari 64 KB pertama, lalu kolom diberikan eksplisit agar baris pembuka yang lebih sempit tidak mengacaukan deteksi.

## Lolos/tidak terhadap target

- **AC 2 (RSS > 2 GB → mitigasi):**
  - DuckDB melewati 2 GB (2.266 MB) dan gagal di batas D7 1 GB. ExcelJS gagal.
  - Parser terpilih sax-yauzl + spill: 639 MB, di bawah 1 GB.
  - Lihat ADR-0005.
- **Waktu:** 351 s untuk parse xlsx 1 GB masuk rentang perkiraan flow-kerja C (5–15 menit ingest). T-024 mengukur alur penuh terhadap target < 20 menit. Ruang optimasi bila perlu: pemindai `<c>`/`<v>` khusus menggantikan SAX umum, dan cache LRU shared strings yang lebih besar.
