- Mesin: container cloud sesi Claude — Intel Xeon @ 2,10 GHz, 4 vCPU, 15 GiB RAM, disk virtio
  (`vda`, 256 GB), Node 22.23.3. **Bukan VM olympus**: ulang di VM dengan `scripts/perf-period-cycle-vm.sh`

- Jalur: produksi utuh pada dev stack — PostgreSQL 16, RustFS, Redis, worker sungguhan

## AC1 — durasi unggahan ke-N dan objek baru per unggahan

"Proses" = complete → versi READY aktif (diukur poll 200 ms; `workerS` = ingestStartedAt→FinishedAt);
"total" = transfer + proses + Terapkan (bila ditinjau).

| Seri | Unggahan ke-1 | Min | Median | Maks | Maks / ke-1 | Target |
|---|---|---|---|---|---|---|
| 400 rb baris (24×), proses | 22,72 s | 22,32 s | 23,03 s | 23,57 s (ke-12) | **1,037** | ≤ 1,2 ✓ |
| 400 rb baris, total | 23,03 s | 22,57 s | 23,30 s | 23,85 s | 1,036 | ≤ 1,2 ✓ |
| 1 jt baris (10×, tiap kali melepas 2–3 bulan), proses | 47,91 s | 47,66 s | 48,44 s | 49,92 s (ke-4) | **1,042** | ≤ 1,2 ✓ |
| 1 jt baris, total (+ Terapkan 0,10–0,32 s) | 48,68 s | 48,34 s | 49,2 s | 50,64 s | 1,040 | ≤ 1,2 ✓ |

Durasi tidak naik dengan jumlah periode yang sudah ada (unggahan ke-24 di atas 23 periode: 22,92 s;
unggahan 1 jt ke-10 di atas 9,2 jt baris aktif: 47,81 s). Unggahan ke-1 (REPLACE ke dataset kosong,
inferensi) setara unggahan periode berikutnya; "Atur periode" 400 rb baris: 21,56 s.

Objek baru per unggahan (selisih daftar objek `raw/<ds>/` + `parquet/<ds>/` sebelum/sesudah):

| Unggahan | Parquet periode (raw + typed, metadata) | Objek parquet baru | Rasio | Objek lama berubah / hilang | File asli baru |
|---|---|---|---|---|---|
| ke-1 (REPLACE + Atur periode) | 4,2 MB | 8,3 MB | 1,99 | 0 / 0 | 28,2 MB |
| ke-2 … ke-24 (400 rb) | 4,1 MB | 4,1 MB | **1,000** setiap unggahan | 0 / 0 | 28,3 MB |
| ke-25 … ke-34 (1 jt, + pelepasan) | 10,2–10,3 MB | 10,2–10,3 MB | **1,000** setiap unggahan | 0 / 0 | 70,8 MB |

Unggahan ke-1 menulis dua kali (segmen legacy versi REPLACE + segmen periode dari "Atur periode"); segmen
legacy dibuang retensi + GC seperti periode lain. Pelepasan/penggantian tidak menghapus objek saat itu
(masih dirujuk versi tersimpan); data aktif stabil ± 100–102 MB (10 × 1 jt baris).

## AC2 — retensi + GC setelah 34 unggahan, job invarian

Retensi versi (3 versi siap terakhir; tenggang 1 jam dilompati), retensi file asli (7 hari dilompati),
`segment-gc` dua putaran (tenggang 24 jam dilompati), `storage-cleanup`, lalu `segment-audit` (job
invarian malam), semuanya fungsi job worker yang sama. Sejak review putaran 1 setiap job berjam-maju
dibatasi ke dataset perf (parameter `datasetId` baru, diuji); `segment-audit` berjalan apa adanya.

## AC4 — pertambahan backup per unggahan (proksi; backup sungguhan menunggu VM)

Backup harian = `pg_dump` + salinan seluruh bucket (tar → age, tanpa kompresi tambahan), jadi pertambahan
arsip ≈ pertambahan bucket + dump. Dari tabel di atas: malam setelah unggahan 400 rb baris arsip tumbuh
± 32,4 MB (file asli 28,3 MB + parquet 4,1 MB); setelah file asli lewat 7 hari tinggal **≈ 4,1 MB =
parquet periodenya** (+ < 10 KB metadata DB). Bulan 1 jt baris: ± 81 MB lalu ≈ 10,2 MB. Ini proksi;
`scripts/perf-period-cycle-vm.sh` menjalankan backup harian sungguhan stack uji di titik 0, 1, 2, 3, 24,
34 dan setelah pemeliharaan (`backup.tsv`) untuk membuktikannya di VM. Rumus ukuran disk: runbook §8.

## Catatan

- Satu putaran (bukan median beberapa putaran); variasi antar-unggahan ±3%, jauh di bawah ambang 20%.
- Pembuatan CSV di skrip (± 30 s/bulan 400 rb) tidak termasuk waktu unggahan.
- Dataset perf dihapus di akhir putaran (penghapusan dataset biasa).
- Putaran penuh di atas masih memakai job pemeliharaan TANPA batas dataset (diperbaiki setelahnya, lihat
  AC2). Dampak di dev diperiksa: saat itu database hanya berisi dataset perf + dataset 10 jt T-061
  (`segment-gc` datasets = 2). Dataset T-061 tidak punya file asli (`sourceKey` null, `sourceDeletedAt`
  tetap null) dan 24 segmennya tetap tanpa tanda `unreferencedAt`; `raw-retention` menghapus 3 file asli =
  persis 3 versi hidup dataset perf. Jadi tidak ada data lain yang terdampak di dev, tetapi versi lama
  skrip TIDAK aman untuk database bersama. Putaran kecil ulang (3 × 20 rb + 2 × 30 rb) dengan job terbatas:
  storage = dirujuk (rasio 1,0000), GC datasets = 1, audit missing 0.
