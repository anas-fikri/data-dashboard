# T-061 — Performa dan beban "Lihat data" pada 10 jt dan 13 jt baris (P-29)

- **Tanggal / commit:** 2026-10-20/21, basis `69fdcf7` + skrip T-061 (tanpa perubahan kode aplikasi).
- **Mesin (BUKAN VM T-023):** container cloud sesi Claude — 4 vCPU Intel Xeon @ 2,10 GHz, RAM 16 GB, SSD,
  Linux 6.18, Node 22.23.3, DuckDB 1.5.6 (`@duckdb/node-api`). Mesin dipakai satu proses perf pada satu waktu
  (load 1 menit 0,9–3,6 selama run; lebih tinggi saat uji beban). Profil VM T-023 = 4 vCPU/16 GB: jumlah inti
  sama, tetapi disk/CPU olympus berbeda — **AC yang menyebut profil T-023 tetap menunggu run pemilik di VM**
  (`scripts/perf-grid-vm.sh`, lihat bawah).
- **Data** (`scripts/perf-grid-data.ts`, deterministik, tata letak typed ingest: zstd, row group 122.880,
  `_row BIGINT` = rowBase + baris fisik, `_src_row`): 30 kolom = 10 teks (resi unik, kota 10 nilai, layanan,
  pelanggan 200 rb nilai, kurir, cabang, status, SKU, catatan 1 jt nilai, alamat), 10 desimal(38,6), 5 bilangan
  bulat, 5 tanggal; nilai acak (hash) agar urut tidak "gratis".

| Fixture | Bentuk | Ukuran parquet |
|---|---|---|
| 10 jt periode | 24 segmen bulanan × ±417 rb, `_period`, sheet periode sumber LABEL | 915 MB |
| 10 jt satu file | 1 file, sheet non-periode (REPLACE) | 947 MB |
| 13 jt periode | 13 segmen × 1 jt (bentuk YoY 13 bulan, Q2) | 1.190 MB |

## Cara mengukur

1. **Jalur server** — `npm run perf -- grid --dir <scratch> [--rows 13000000 --segs 13] [--layout single]
   --reps 30 --load [--grid-slots 1] --json <f>`: `runGridRows`/`runGridValues`/`runGridStats` sungguhan,
   `QueryEngine` produksi (memory_limit 1 GB, 2 thread, 4 slot global, 2 per user, sandbox), `ParquetCache`
   hangat. 30 putaran per skenario; p95 = nilai ke-⌈0,95·n⌉. "Pertama" = rowStart 0 dengan cache count kosong
   (permintaan pertama setelah ganti urut/saring); "dalam" = posisi acak di 25–100 % hasil, count sudah di-cache.
2. **Ujung-ke-ujung** — `scripts/dev-grid-perf-seed.ts` memasang fixture 10 jt periode ke Postgres + RustFS dev
   sebagai segmen sungguhan (Dataset/versi READY/Sheet/Segment/SegmentTyped/manifest + dashboard berbagi
   EDITOR ke 5 akun), lalu `scripts/perf-grid-http.mjs` mengukur `POST /api/sheets/:id/rows` (sesi, rate limit,
   repo Prisma, cache parquet aplikasi, gerbang grid), halaman `/datasets/:id/data` di Chromium headless
   (waktu sampai baris berisi data terlihat), dan beban 5 penggulir (akun editor, patuh rate limit 280/menit)
   + dashboard 6 widget lewat `/api/query` (filter kota acak tiap putaran → cache hasil dingin).
   Server = **`next dev`** (Turbopack; produksi menolak start tanpa https) — angka HTTP/UI di sini pesimis
   (React dev build, overhead rute dev ±5–70 ms).

## Temuan dan analisis

1. **Blok tanpa urut jauh di bawah target** (p95 server 31–74 ms; lewat HTTP dev 170 ms). "Ke baris" dan gulir
   tidak dibatasi server.
2. **Blok pertama urut ≈ 2,3–3,3 s di 10 jt — tepat di batas 3 s; 13 jt melewatinya (3,1–3,9 s).** Profil query
   (`EXPLAIN ANALYZE`, data 10 jt): tahap `ids` (urut `_row` + kunci, LIMIT 200) hanya 0,2–0,5 s; **±2 s habis di
   tahap ambil isi** `WHERE _row IN (ids)`: 200 baris acak tersebar di hampir semua 82 row group, jadi DuckDB
   mendekompresi halaman zstd ke-30 kolom (desimal(38,6) termahal, ±1 s untuk 10 kolom desimal). Dicoba: daftar
   `_row` sebagai literal/`list_contains($ids)` (filter terdorong ke scan) → tahap ambil tetap ±1,9 s, dan dengan
   kolom keluaran aplikasi justru 2× lebih lambat (4,8–8,1 s); `TopN` langsung 2,6 s. Bukan bug kode yang bisa
   diperbaiki kecil: biaya sebanding jumlah kolom yang diminta × row group yang tersentuh.
3. **Blok dalam urut teks p95 6,0 s (10 jt) / 7,9 s (13 jt) > 2 s → P-30 (T-062) diaktifkan** (AC4). Catatan
   untuk T-062: berkas permutasi `_row` hanya menghapus tahap `ids` (±3–3,5 s dari 5,5 s); tahap ambil ±2 s
   tetap ada, jadi target T-062 "≤ 500 ms" tidak tercapai tanpa juga memangkas kolom yang diambil (mis. minta
   hanya kolom yang terlihat di viewport, saat ini klien meminta semua kolom terlihat skema, ≤ 64 per potongan)
   atau menyimpan baris hasil dalam urutan permutasi.
4. **Isolasi beban:** gulir polos lolos (rasio 1,21–1,24, tanpa BUSY/TIMEOUT widget). Penggulir yang semuanya
   gulir dalam urut teks (skenario stres) membuat widget 2,17–2,20× lebih lambat: 2 slot grid × 2 thread DuckDB
   + 2 slot widget × 2 thread = 8 thread di 4 vCPU (CPU, bukan antrean — widget 0 BUSY). Dengan
   `GRID_MAX_CONCURRENCY=1` rasio 1,04 / 1,67 (lolos) dengan biaya blok grid di bawah beban p95 389 → 587 ms.
   **Rekomendasi untuk VM 4 vCPU: `GRID_MAX_CONCURRENCY=1`** (bawaan 2 dibiarkan; putuskan dari run VM, olympus
   saat ini 8 vCPU).
   **Status AC2: belum lolos dengan setelan bawaan.** Lolos: gulir polos (2 slot 1,21 server / 1,68 HTTP; 1 slot
   1,04), gulir dalam urut teks dengan 1 slot (1,67). Gagal: gulir dalam urut teks dengan bawaan 2 slot (2,17
   server / 2,25 HTTP; 13 jt 2,20). Menunggu run VM T-023 (`perf-grid-vm.sh` mengukur 2 dan 1 slot).
5. **13 jt (Q2):** blok tanpa urut, saring, periode, ringkasan tetap jauh di bawah target; urut/saring+urut blok
   pertama melewati 3 s (3,1–3,9 s) dan blok dalam urut teks 7,9 s. **Di 4 vCPU, `PERIOD_SHEET_MAX_ROWS` jangan
   dinaikkan ke 13 jt** sebelum run VM dan/atau T-062; lihat juga rasio beban 2,20× pada varian stres.

## Ulang ukur di VM (pemilik)

```bash
bash deploy/perf-stack.sh up 6          # stack uji terpisah, 6 akun
bash scripts/perf-grid-vm.sh hasil-T-061 30
bash deploy/perf-stack.sh down
```

`scripts/perf-grid-vm.sh` menjalankan jalur server yang sama di container worker image produksi (10 jt periode +
beban grid 2 dan 1 slot, 10 jt satu file, 13 jt + beban), lalu memasang 10 jt dan 13 jt ke stack uji dan
menjalankan `perf-grid-http.mjs` dari image renderer lewat proxy TLS (server produksi, bukan dev). Disk sementara
± 8 GB di `$PERF_DIR/grid`. Salin `hasil-T-061/` ke `docs/ai/perf/T-061-olympus/`.
