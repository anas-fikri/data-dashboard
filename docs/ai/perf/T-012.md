# T-012 — Perf filter dashboard (1 juta baris)

- **Tanggal / commit:** 2026-10-14, HEAD `1c4ecfb` + perbaikan review putaran 1 yang belum di-commit (not_in, kecocokan tipe, kunci cache slicer ternormalisasi).
- **Mesin:** Apple M4 (10 core), RAM 16 GB, SSD lokal; Node 26; DuckDB 1.5.6. Mesin query sama dengan produksi: `memory_limit` 1 GB, `threads` 2, 2 query per user, 4 global, sandbox `allowed_directories`. **Mesin sedang sibuk:** dev server, worker, dan sesi lain ikut berjalan, dengan load average 2,6 di awal dan 2,5 di akhir pengukuran (rata-rata 5 menit sekitar 4,3).
- **Perintah:** `npx tsx --conditions=react-server scripts/perf-filters.ts`. Skrip membuat parquet 1.000.000 baris langsung dengan DuckDB (row group 122.880, zstd) di folder sementara, lalu menghapusnya di akhir. Query widget dijalankan lewat `runWidgetQuery` (sama dengan `/api/query { widgetId, dashboardFilters }`), dan slicer lewat `runFilterValues` (sama dengan `POST /api/dashboards/[id]/filter-values`). **Cache hasil dimatikan**, jadi setiap permintaan menjalankan DuckDB. Setiap skenario diulang 7 kali.
- **Data:** Kota (teks, **50.000 nilai unik**; 5.000 di antaranya mengandung "jak"), Layanan (teks, 5 nilai), Omzet (DECIMAL(38,6)), Tanggal (DATE, 650 hari), Waktu (TIMESTAMP). Parquet hanya 8 MB karena data sintetis mudah dikompres. Untuk data nyata yang lebih besar, rujukan batas atasnya adalah tabel lebar 433 MB di [T-011](T-011.md).
- **Widget (6):** KPI jumlah baris, KPI total Omzet, batang Omzet per Layanan, garis Omzet per bulan (grain), batang 20 Kota teratas (50.000 kategori + query total), dan tabel 4 kolom halaman 1 (count + halaman).
- **Set filter:** 0 filter; 1 filter (`in` 2 nilai Kota); 3 filter (`in` 2 nilai Layanan + rentang Omzet 10.000–400.000 + preset YTD Tanggal, hari ini 2026-10-14 WIB).

## Hasil

| Skenario | p50 | p95 | maks |
|---|---|---|---|
| Semua query widget (126×: 6 widget × 3 set filter × 7) | 13 ms | 36 ms | 38 ms |
| Widget, 0 filter (42×) | 6 ms | 37 ms | 38 ms |
| Widget, 1 filter `in` 2 nilai (42×) | 14 ms | 27 ms | 28 ms |
| Widget, 3 filter `in` + rentang + YTD (42×) | 13 ms | 28 ms | 28 ms |
| Satu perubahan filter = 6 widget paralel (jatah 2/user, 3 user), 0 filter | 53 ms | 56 ms | 56 ms |
| Satu perubahan filter = 6 widget paralel, 1 filter | 53 ms | 55 ms | 55 ms |
| Satu perubahan filter = 6 widget paralel, 3 filter | 47 ms | 51 ms | 51 ms |
| Slicer Kota, halaman pertama (DISTINCT 50.000 → 1.000 + truncated) | 15 ms | 16 ms | 16 ms |
| Slicer Kota, cari "jak" (strip_accents + LIKE, 5.000 cocok → 1.000 + truncated) | 30 ms | 31 ms | 31 ms |
| Puncak RSS proses (buat parquet + semua query) | 195 MB | | |

Widget paling lambat adalah batang 20 Kota teratas tanpa filter (p95 38 ms), karena grafik ini mengelompokkan 50.000 kategori lalu menghitung total kategori secara terpisah. Filter justru mempercepatnya (28 ms dengan 3 filter).

## Lolos/tidak terhadap target

- **Target interaktif (< 2 detik p95):** **lolos dengan margin besar.** p95 query widget 36 ms, satu dashboard 6 widget 56 ms, dan slicer dengan kata cari 31 ms, semuanya tanpa cache hasil dan saat mesin sibuk.

## Catatan

- Di aplikasi, permintaan yang sama dilayani cache hasil. Kuncinya memuat klausa filter kanonik, jadi urutan nilai atau urutan filter yang berbeda tetap memakai entri yang sama. Kunci slicer memakai kata cari yang sudah dinormalkan (NFC, huruf kecil, tanpa aksen), dan daftar nilai > 256 KB tidak di-cache.
- Slicer yang dibatalkan klien (ketikan berikutnya) tidak menjalankan DuckDB bila masih antre, dan yang sedang berjalan di-interrupt.
- Belum diukur di sini: banyak user bersamaan dan parquet ratusan MB per sheet. Keduanya masuk uji beban T-024.
