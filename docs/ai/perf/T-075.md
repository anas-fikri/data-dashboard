# T-075 — pivot lanjutan pada 10 jt baris + dashboard 6 widget terikat (G-7 fase 5)

Syarat (AC2 T-075, rencana G-7 §6 R2 dan §8 Q4): p95 pivot 4 tingkat × 8 nilai + Top N + field terhitung
≤ 3 s pada 10 jt baris (profil T-023, cache hangat), dashboard 6 widget terikat satu sumber tanpa widget
lain kena QUERY_TIMEOUT, dibanding baseline T-009/T-011. Aturan cadangan T-070: bila 4×8 > 2× pivot 2×3,
turunkan `PIVOT_VALUES_MAX` ke 6.

**Kesimpulan singkat:** rasio 4×8 vs 2×3 **1,76–1,77× (lulus ≤ 2×)** → cadangan "6 nilai" **tidak dipicu**,
batas bawaan tetap 4 tingkat × 8 nilai. Target mutlak **p95 ≤ 3 s TIDAK terpenuhi di mesin ini**: pivot
2×3 yang sudah ada sejak 1.0.0 saja p95 4,6 s; 4×8 8,1–8,2 s; 4×8 + Top N + terhitung + tampil sebagai
10,4–10,6 s. Tidak ada QUERY_TIMEOUT (batas 30 s) maupun QUERY_BUSY yang lolos ke pengguna. Pengukuran di
profil produksi (olympus, T-023) belum dilakukan — perlu pemilik (lihat "Yang harus diukur di olympus").

## Cara ukur

`npm run perf -- pivot-lanjutan 10000000 10` (= `npx tsx --conditions=react-server
scripts/perf-pivot-advanced.ts 10000000 10`; `PERF_PART=A` / `PERF_PART=B` untuk satu bagian).

- Data `scripts/perf-grid-data.ts` (sama dengan T-061/T-070): satu file parquet 10 jt baris × 30 kolom,
  947 MB, zstd, row group 122.880 (`tests/fixtures/perf/pivot/`, gitignored; dibangkitkan ± 2 mnt).
- Jalur sungguhan **`runWidgetQuery`** (body `{ widgetId }` seperti `/api/query`): otorisasi repo (palsu
  in-memory, peran VIEWER) → spec efektif pivot tersimpan (`effectiveConfig`) → `widgetPlan` → DuckDB →
  bentuk hasil → cache hasil. Bedanya dengan T-070: T-070 memanggil `buildPivotSql` langsung (tanpa
  query total/antrian/cache).
- Mesin query setelan produksi (`runtime.ts`/`.env.example`): `QueryEngine` memory_limit 1 GB, 2 thread
  per query, `MAX_QUERY_CONCURRENCY` 4, 2 slot per user, antre ≤ 10 s, `QUERY_TIMEOUT_MS` 30 s, sandbox;
  cache parquet lokal (hard link, tanpa unduh S3); cache hasil 64 MiB (`QUERY_RESULT_CACHE_BYTES` bawaan).
- Mesin: kontainer cloud 4 vCPU, 15 GB RAM, SSD, Node 22.23.3 (bukan olympus; tanpa beban aplikasi lain).
- Spec (semua: kolom pemisah Tanggal 26 per bulan = 24 kolom, urut nilai turun, Total + Subtotal):
  - 2×3: Kota Tujuan (10) › Layanan (6); Total Nilai 11, Jumlah baris, Rata-rata Nilai 12.
  - 4×8 (= T-070): Kota Tujuan › Layanan › Status (5) › Cabang (300) → 90.000 baris terdalam (200 tampil);
    3 nilai di atas + Terkecil, Terbesar, Total Jumlah 21, Jumlah unik Kurir (2.000), Margin (terhitung).
  - "+ terhitung + tampil sebagai": Total Nilai 11, Jumlah baris **total berjalan**, Rata-rata, Total Nilai
    11 **% dari total kolom**, Terbesar, Jumlah unik, **Laba** (Σ11 − Σ12) dan **Margin** (terhitung).
  - "+ Top 10": Top 10 Cabang per Status (menurut nilai 1) + "(Lainnya)" dihitung ulang dari baris mentah.

## A. Satu widget pivot, tanpa cache hasil (10 putaran bergantian + 1 pemanasan)

Putaran 1:

| Spec | p50 (ms) | p95 (ms) | Rasio p95 vs 2×3 | Hasil |
|---|---|---|---|---|
| 2 tingkat × 3 nilai (baseline) | 4.488 | 4.577 | 1,00 | 60/60 baris, 24/24 kolom |
| **4 tingkat × 8 nilai (T-070)** | 7.546 | 8.091 | **1,77** | 200/90.000 baris, 14/24 kolom |
| 4 × 8 + Top 10 Cabang | 9.417 | 10.786 | 2,36 | 200/3.300 baris, 13/24 kolom |
| 4 × 8 + terhitung + tampil sebagai | 7.801 | 8.630 | 1,89 | 200/90.000 baris, 14/24 kolom |
| **4 × 8 + terhitung + tampil sebagai + Top 10** | 10.114 | 10.639 | 2,32 | 200/3.300 baris, 13/24 kolom |
| 4 tingkat × 6 nilai (cadangan) | 5.277 | 5.613 | 1,23 | 200/90.000 baris, 19/24 kolom |

Putaran 2 (ulang, mesin sama):

| Spec | p50 (ms) | p95 (ms) | Rasio p95 vs 2×3 |
|---|---|---|---|
| 2 tingkat × 3 nilai (baseline) | 4.421 | 4.676 | 1,00 |
| **4 tingkat × 8 nilai (T-070)** | 7.790 | 8.211 | **1,76** |
| 4 × 8 + Top 10 Cabang | 9.337 | 10.261 | 2,19 |
| 4 × 8 + terhitung + tampil sebagai | 7.842 | 8.240 | 1,76 |
| **4 × 8 + terhitung + tampil sebagai + Top 10** | 10.085 | 10.412 | 2,23 |
| 4 tingkat × 6 nilai (cadangan) | 5.286 | 5.598 | 1,20 |

Overhead per fitur (p95 terhadap 4×8 biasa, putaran 1/2): field terhitung + tampil sebagai **+7 % / +0 %**
(praktis gratis: dihitung atas agregat yang sama); **Top N +33 % / +25 %** (agregat kedua atas baris
mentah untuk "(Lainnya)" + peringkat per induk). Rasio Top N > 2× bukan pemicu cadangan "6 nilai" (aturan
T-070 tentang jumlah nilai; 6 nilai tidak mengurangi biaya Top N) — dicatat sebagai risiko, bukan diubah.

Pembanding 1 jt baris (T-070, `buildPivotSql` langsung): 2×3 p95 615–630 ms, 4×8 1.203–1.252 ms (1,96–
1,99×). Pada 10 jt rasionya justru turun (1,76×): biaya tetap per pindaian (proyeksi + dekompresi kolom)
mendominasi kedua spec, jadi waktu tumbuh ± linear dengan baris (2×3: 7,3×; 4×8: 6,6× untuk 10× baris).

## B. Dashboard 6 widget terikat SATU pivot tersimpan (5 putaran)

Pivot tersimpan = spec "4 × 8 + terhitung + tampil sebagai + Top 10" (total berjalan diganti % total
keseluruhan, lihat temuan 2). Widget: pivot, tabel (rata, tanpa kolom pemisah), batang (Kota Tujuan,
Margin, 10 teratas), garis (per bulan), pai (5 + Lainnya), KPI (Jumlah unik). Dibuka seperti browser
(`widget-query.ts`): ≤ 2 query widget berjalan per halaman, QUERY_BUSY dicoba ulang 2× dengan jeda.
Waktu per widget = sejak halaman dibuka sampai jawaban (termasuk antre). Dingin = cache hasil kosong;
hangat = halaman dibuka lagi (cache hit); revisi = pivot tersimpan disimpan ulang (revisi naik → kunci
cache baru → semua miss).

| Widget | Dingin p50 / p95 (ms) | Hangat (hit) p50 / p95 (ms) | Revisi naik (miss) p50 / p95 (ms) |
|---|---|---|---|
| pivot | 11.919 / 12.258 | 2 / 4 | 11.035 / 12.517 |
| tabel | 6.400 / 7.541 | 2 / 4 | 6.671 / 7.445 |
| batang | 7.489 / 8.526 | 3 / 5 | 7.864 / 8.641 |
| garis | 9.312 / 10.434 | 3 / 5 | 9.954 / 10.231 |
| pai | 10.216 / 11.427 | 4 / 6 | 10.954 / 11.080 |
| kpi | 10.849 / 11.817 | 4 / 6 | 11.384 / 11.786 |
| **seluruh dashboard (p50 / maks)** | **11.919 / 12.258** | **4 / 6** | 11.394 / 12.517 |

- **QUERY_TIMEOUT: tidak ada; QUERY_BUSY yang sampai ke pengguna: tidak ada** (puncak RSS 683 MB).
- Cache hit 2–6 ms per widget: revisi pivot tersimpan di kunci cache bekerja (miss tepat setelah simpan,
  hit sesudahnya), sama dengan perilaku T-073.
- Pengamatan (bukan skenario browser): bila keenam query dikirim **sekaligus** tanpa batas 2 per halaman,
  KPI mendapat **QUERY_BUSY** (2 slot per user, antre > 10 s). Browser aman karena `widget-query.ts`
  membatasi 2 + coba ulang; klien lain (skrip/API) yang menembak paralel akan melihat 429.

Pembanding baseline: T-009 (10 jt baris CSV, 2 dimensi + 2 ukuran, M4 10 core) p95 608 ms; T-011 tabel
1 jt baris maks 99 ms (sempit) / 791 ms (lebar). Pivot 10 jt baris di sini 7–17× lebih lambat dari T-009:
kolom pemisah 24 bulan + total/subtotal/kolom Total (GROUPING SETS) + parquet 30 kolom, dan mesin 4 vCPU
(bukan M4).

## Lolos/tidak terhadap AC2

| Syarat | Hasil | Status |
|---|---|---|
| p95 pivot 4×8 + Top N + terhitung ≤ 3 s (10 jt, cache hangat) | Cache **hangat** (hit): 2–6 ms. Tanpa cache (permintaan pertama / setelah simpan / filter baru): **10,4–10,6 s** | Lolos hanya untuk hit; permintaan dingin **tidak** |
| Tidak ada widget lain kena QUERY_TIMEOUT (dashboard 6 widget) | 0 timeout, 0 BUSY ke pengguna; dashboard dingin ± 12 s | Lolos |
| Rasio 4×8 vs 2×3 ≤ 2× (aturan cadangan T-070) | 1,76–1,77× | Lolos → `PIVOT_VALUES_MAX` tetap 8 |
| Profil T-023 (olympus) | Belum diukur | **Menunggu pemilik** |

Keputusan default yang aman (catatan kerja: tidak mengubah batas tanpa bukti): batas 4 tingkat × 8 nilai dan
Top N **tidak diubah**. Angka dingin > 3 s juga berlaku untuk pivot 2×3 lama (4,6 s), jadi bukan regresi G-7;
perbaikan menyeluruh (pra-agregasi/pemanasan cache setelah aktivasi, satu agregat dasar dipakai bersama
widget terikat satu sumber) adalah perubahan arsitektur → task lanjutan **T-hfqf**, bukan T-075.

## Temuan dari uji T-075

1. **Halaman cetak pivot 4 tingkat di kartu kecil**: kartu ukuran bawaan menampilkan "Menampilkan 0 dari
   32 baris" (hanya kepala kelompok yang muat). Ada catatan, jadi tidak diam-diam — tetapi PDF tidak
   berguna; e2e memakai kartu 12×16 (pivot terbesar). Task lanjutan **T-7ykh**.
2. **Tabel terikat + total berjalan + Top N di baris terdalam**: pivot tersimpan dengan kolom pemisah sah,
   tetapi widget tabel membuang kolom pemisah → spec efektif ditolak (TOP_N_AXIS_TEXT) dengan pesan "Pilih
   ulang nilai" yang tidak bisa diperbaiki dari panel tabel. Task lanjutan **T-hbcp**.
3. Diperbaiki di T-075: kontras label pratinjau editor field terhitung (muted-foreground di atas bg-muted
   4,39:1, axe serious) dan aksi kepala dashboard meluap 195 px di 768 px (aksi kini boleh turun baris).

## Yang harus diukur di olympus (pemilik)

- PDF sungguhan (renderer Chromium): di kontainer cloud renderer tidak bisa jalan (root tanpa
  `--no-sandbox`), jadi e2e menguji halaman cetak `/render/<token>` yang dibuka renderer (siap < 60 s =
  `RENDER_TIMEOUT_MS` bawaan; di dev ± 5–10 s). Di olympus: ekspor PDF dashboard e2e (pivot 12×16, 4 tingkat)
  dan catat durasi job vs `RENDER_TIMEOUT_MS`.
- `npm run perf -- pivot-lanjutan 10000000 10` di VM produksi (8 vCPU, HDD bersama, `GRID_MAX_CONCURRENCY=1`)
  untuk angka profil T-023; skrip butuh ± 2 GB disk sementara untuk fixture.
