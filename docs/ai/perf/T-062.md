# T-062 — Cache urutan "Lihat data" (P-30)

- **Tanggal / commit:** 2026-10-21, basis `e94e670` + kode T-062.
- **Mesin (BUKAN VM T-023):** container cloud sesi Claude yang sama dengan T-061 — 4 vCPU Intel Xeon @
  2,10 GHz, RAM 16 GB, Node 22.23.3, DuckDB 1.5.6. Satu proses perf pada satu waktu (load 1 menit 0,9–4,0).
- **Data:** fixture T-061 `10 jt periode` (24 segmen bulanan, 30 kolom, 915 MB, `scripts/perf-grid-data.ts`).
- **Perintah:** `npm run perf -- grid --dir <scratch> --reps 30 --only "cache,urut teks pertama,urut teks
  dalam,acak" --load --keep --json docs/ai/perf/T-062/10m-period.json` (mesin produksi: memory_limit 1 GB,
  2 thread, 4 slot, cache parquet hangat; `GRID_ORDER_CACHE_BYTES` 1 GiB).

## Kenapa permutasi saja tidak cukup (eksperimen DuckDB langsung, 2 thread)

| Langkah (10 jt, urut teks pelanggan) | Waktu | Ukuran |
|---|---|---|
| Bangun permutasi `COPY (SELECT _row … ORDER BY …)` | 3,6 s | 37 MB |
| Baca 200 posisi dari permutasi (`file_row_number BETWEEN`) | 4–9 ms | — |
| Ambil isi 200 `_row` acak dari sumber (30 kolom) | 2,3–2,5 s | — |
| Ambil isi 10 rb / 50 rb / 100 rb `_row` dari sumber + tulis potongan | 2,9 / 3,1 / 3,2 s | 1,1 / 5,4 / 10,7 MB |
| Baca 200 baris dari potongan terurut | 7–14 ms | — |
| Salinan sumber row group 4.096 (urutan asli) + `_row IN` 200 nilai | 0,5 s | 961 MB |
| Salinan terurut penuh (ORDER BY lebar) | 49 s bangun, 0,17 s baca | 1.059 MB |
| Salinan terurut penuh dipartisi per posisi (`PARTITION_BY`) | Out of Memory pada 1 GB | — |

Biaya ambil isi didominasi dekompresi zstd semua row group sumber (200 baris acak menyentuh hampir semua
82 row group), hampir tidak bergantung pada jumlah baris yang diambil. Salinan penuh (terurut atau
row group kecil) ±1 GB per tampilan — melewati anggaran 1 GiB dan butuh 21–49 s CPU. Karena itu desainnya:
**berkas permutasi + potongan terurut 50 rb baris yang diambil isinya sekali** (biaya ±1 blok tanpa cache),
lalu blok di potongan itu dibaca dalam milidetik.

## Desain

- `src/features/query/order-cache.ts`: indeks entri di memori + berkas di `<QUERY_CACHE_DIR>/order`
  (dikosongkan saat proses mulai). Kunci = sheet + versi + revisi skema + file typed segmen (setelah pemilih
  periode) + urut + saringan + cari + periode. LRU byte (`GRID_ORDER_CACHE_BYTES`, bawaan 1 GiB; berkas yang
  sedang dibaca dipin), TTL 30 menit sejak terakhir dipakai, `invalidate` saat versi/revisi berganti
  (VERSION_CHANGED membuang semua entri sheet itu), `forget` saat data dihapus.
- `src/features/query/grid-order.ts`: permintaan jalur 2 (urut/cari) tanpa entri dijawab jalur lama lalu
  menjadwalkan permutasi di belakang (satu per proses, gerbang grid dengan pengguna semu, tanpa sinyal
  permintaan). Blok berikutnya: potongan (`orderChunkRows`: 50 rb baris untuk ≤ 30 kolom, min 5 rb) yang belum
  ada diambil isinya dari sumber dan ditulis urut posisi; blok dibaca dengan `_pos BETWEEN`. Kolom keluaran =
  ekspresi grid (teks dipotong 500 + penanda), jadi jawaban identik (uji properti
  `tests/features/query/grid-order.test.ts`).
- Saring tanpa urut/cari tidak di-cache (sudah ≤ 0,5 s di T-061).

## Hasil (p50 / p95 / maks, ms, 30 putaran)

| Skenario | p50 | p95 | maks | Target |
|---|---|---|---|---|
| **Urut teks, blok berikutnya (cache)** | 16 | **24** | 39 | ≤ 500 (AC1) |
| Urut angka, blok berikutnya (cache) | 16 | 21 | 26 | — |
| Saring + urut teks, blok berikutnya (cache) | 17 | 23 | 24 | — |
| Urut teks dalam, lompat acak (cache, potongan baru) | 3.019 | **3.276** | 3.332 | ≤ 500 **tidak tercapai** |
| Bangun permutasi teks di belakang (sesudah blok pertama) | 3.963 | 4.187 | 4.200 | — |
| Urut teks dalam tanpa cache (pembanding T-061: 6.032) | 6.148 | 6.493 | 6.516 | — |
| Urut teks blok pertama tanpa cache (T-061: 2.847) | 3.084 | 3.364 | 3.608 | ≤ 3.000 |
| Blok tanpa urut, acak (T-061: 53) | 53 | 81 | 101 | ≤ 300 |

"Blok berikutnya" = blok sesudah sebuah lompatan acak di 25–100 % hasil (gulir lanjutan, potongan sudah ada),
setelah permutasi selesai dibangun. "Lompat acak" = posisi acak baru (hampir selalu potongan yang belum ada).
Blok pertama urut tidak diubah T-062 (jalur lama); selisih 2,85 → 3,36 s terhadap T-061 terjadi pada jalur
yang sama tanpa cache (run lain, load mesin lebih tinggi) — tetap di batas target, diulang di VM.

### Beban: 5 penggulir (2 in-flight) + dashboard 6 widget, grid 2 slot

| Varian | p95 widget baseline / beban | Rasio | BUSY/TIMEOUT widget | Blok grid ok / BUSY, p50 / p95 |
|---|---|---|---|---|
| Gulir polos | 692 / 823 | 1,19 | 0 / 0 | 681 / 0, 360 / 446 ms |
| Gulir dalam urut teks tanpa cache (T-061) | 665 / 1.463 | 2,20 | 0 / 0 | 12 / 30, 17,5 / 19,2 s |
| Urut teks + cache urutan (lompat acak lalu 4 blok berikutnya) | 677 / 1.466 | 2,17 | 0 / 0 | 32 / 24, 10,2 / 20,5 s |

Dengan cache, penggulir menyelesaikan 2,7× lebih banyak blok, tetapi skenario stres ini (10 alur yang
semuanya terus melompat ke posisi acak baru) tetap jenuh CPU: setiap lompatan membangun potongan ±3 s di
2 slot grid, dan blok murah antre di belakangnya. Rasio widget tidak memburuk (2,17 vs 2,20); rekomendasi
T-061 (`GRID_MAX_CONCURRENCY=1` di 4 vCPU) tetap berlaku.

## Kesimpulan

- **AC1 (blok dalam berikutnya ≤ 500 ms): tercapai untuk gulir lanjutan** — p95 24 ms (teks), 21 ms
  (angka), 23 ms (saring + urut) setelah permutasi siap (±4 s di belakang sesudah blok pertama).
- **Tidak tercapai untuk lompatan ke wilayah baru** (seret scrollbar jauh / "Ke baris" di hasil urut): p95
  3,3 s (turun dari 6,5 s tanpa cache). Batas bawahnya = satu kali dekompresi semua row group sumber;
  menembusnya butuh salinan ±1 GB per tampilan (di atas anggaran 1 GiB, 21–49 s CPU) atau tata letak typed
  dengan row group lebih kecil (perubahan ingest/arsitektur, di luar rencana) — keputusan pemilik.
- **AC2:** dibuktikan uji (bukan perf): `tests/features/query/order-cache.test.ts` (anggaran LRU, TTL,
  invalidasi versi/revisi, forget, pin) dan `tests/features/query/grid-order.test.ts` (revisi naik / versi
  berganti → entri dibuang, versi lain tidak pernah membaca entri lama).
- Angka di VM T-023 belum diukur (lihat T-061 `scripts/perf-grid-vm.sh`; skenario cache urutan ikut otomatis karena bawaan aktif).
