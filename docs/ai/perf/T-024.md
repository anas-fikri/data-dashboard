# T-024 — Uji performa 1 GB ujung-ke-ujung di olympus

- **Tanggal / commit:** 2026-10-17, image produksi dari commit `5b9686c` (build di olympus), klien perf
  `scripts/perf-e2e.mjs` commit `d718d43`+.
- **Mesin (produksi sungguhan, VM bersama):** olympus — container LXC Proxmox, 8 vCPU terbaca (dinaikkan
  user dari 4), RAM 12 GB (dari 8), disk 98 GB di atas **HDD** Proxmox (`sda` ROTA=1), dipakai bersama
  ± 15 container aplikasi lain. Selama uji: load average host 20–57, tekanan I/O (`/proc/pressure/io`
  some) 20–85 %. **Di bawah spek minimum runbook** (SSD, 16 GB).
- **Setelan aplikasi = produksi:** 2 worker × 3 GB (concurrency 1), app 2 GB, renderer 1,5 GB, Redis
  512 MB, DuckDB ingest 2 thread, query `memory_limit` bawaan.
- **Lingkungan uji:** stack terpisah `dashboard-perftest` (`deploy/perf-stack.sh up 5`) di VM yang sama:
  image dan setelan produksi, PostgreSQL container, storage dan volume sendiri, port 9543/9544 —
  data produksi tidak tersentuh. Stack dari volume kosong sampai health hijau + 5 akun: **1 m 53 s**.
- **Klien:** Chromium headless di olympus (image renderer) memakai UI sungguhan (buat dataset, panel
  unggah multipart presigned lewat proxy TLS, buat dashboard) + API publik (10 widget, kolom filter,
  `/api/query`). Memori/CPU container dicatat tiap ± 2 dtk (`scripts/perf-e2e.sh`).
- **Fixture** (`scripts/make-fixture.ts`, parameter `tests/fixtures/README.md`): xlsx teks-berat 935 MB
  (3 sheet × 1 juta baris × 30 kolom, 60 % teks, 70 % unik, baris judul 3, tanggal campuran) dan csv
  974 MB (8,1 juta baris × 10 kolom, titik koma, angka id-ID); antrean: csv 301 MB × 5.

## Lolos/tidak terhadap target

- **AC 1 (total < 20 menit di VM spek minimum):** **tidak terpenuhi di olympus**: xlsx 41,5 mnt; csv ± 17–20 mnt
  sampai dashboard pertama tetapi alur filter gagal (502) dan pengukuran ulang terhenti karena VM macet (catatan 7). Olympus di bawah spek minimum (HDD): ingest xlsx terikat I/O — thread parser sering
  berstatus D (menunggu disk), CPU proses turun ke 30–70 % meski host punya CPU menganggur, tekanan I/O
  cgroup worker ± 20–30 %. Menaikkan batas memori worker ke 5 GB di tengah run tidak mengubah waktu baca
  (sheet 3 8,7 mnt vs sheet 1 8,4 mnt). Perbandingan: komponen yang sama di SSD (Apple M4, T-006) membaca
  xlsx 1 GB dalam 3,3 mnt dan ingest csv 1 GB < 1 mnt.
- **AC 2 (5 upload bersamaan → maks 2 job aktif, sisanya posisi antrean di UI):** **lolos** (lihat di atas).
- **AC 3 (kuota → QUOTA_EXCEEDED dengan angka terpakai/limit):** lolos lewat uji yang ada (lihat
  catatan).

## Catatan dan rekomendasi

1. **Disk SSD adalah perbaikan terbesar** untuk olympus: semua tahap berat (ingest, unduh parquet
   pertama, build image) terikat I/O HDD yang dipakai bersama.
2. Buka dashboard pertama setelah ingest menunggu unduhan parquet ke cache app (xlsx: 3 sheet ±
   600 MB → 109 s di HDD) → task lanjutan: panaskan cache saat versi aktif.
3. Parse xlsx satu thread per file (sheet berurutan) → task lanjutan: parse sheet paralel.
4. Untuk file 1 GB, CSV jauh lebih cepat daripada xlsx (13 vs 37 menit ingest di olympus).
5. Thread DuckDB ingest kini bisa diatur (`INGEST_DUCKDB_THREADS`, bawaan 2): ingest csv dua pertiga
   waktunya jenuh CPU pada 2 thread.
6. AC 3 diuji di `tests/e2e/uploads.spec.ts` (kuota 20 GB, terpakai 18,6 GB siap + 1 GB sedang diunggah,
   file 1 GB baru → ditolak saat init (HTTP 409 QUOTA_EXCEEDED) sebelum ada part terunggah, pesan
   "terpakai 19,6 GB dari 20 GB, file ini 1 GB"); di
   bawah 100 GB angka kini 1 desimal (commit `3586aab`) agar sisa kuota yang kecil tidak terbaca penuh.
7. **Ulang ukur csv dihentikan (2026-10-17).** Run dashboard-saja pada dataset csv 8,1 jt baris sesudah app
   restart: buka dashboard pertama (cache dingin) 198,6 s, memori container app mencapai 1.982 MB dari batas 2 GB,
   lalu `filter-columns` dijawab 502. ± 35 menit kemudian olympus macet ± 4 jam (load ± 180, tekanan I/O penuh,
   swap hampir habis; SSH dan produksi tidak menjawab) sampai VM di-reboot. Dugaan kuat: cgroup app di batas memori
   (page cache ikut dihitung) memaksa reklamasi berulang di HDD bersama. Karena risiko ke produksi dan aplikasi lain
   di VM yang sama, uji berat tidak diulang di olympus; stack uji dan fixture sudah dibongkar.
   Rekomendasi: `APP_MEM` 3 GB untuk dataset ≥ 8 jt baris, disk SSD, dan T-pvq8 (pemanasan cache parquet sesudah
   versi aktif) agar buka dashboard pertama tidak menanggung unduhan + baca dingin.
8. **Perbaikan sesudah uji** (sudah di branch, belum di-deploy ke olympus): pemanasan cache parquet (T-pvq8), parse
   sheet xlsx paralel (T-de1b, baca 21–45 % lebih cepat di SSD), dan proxy tidak 502 saat DNS Docker lambat.
